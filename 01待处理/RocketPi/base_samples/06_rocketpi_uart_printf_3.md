# 06_rocketpi_uart_printf_3

> 进阶补充 3：uart_hexdump 详解——先看它解决什么问题、长什么样，再逐行拆代码实现，读完能自己设计同类函数。
> 前置笔记：[[06_rocketpi_uart_printf]] §uart_hexdump

## 它解决什么问题：printf 看不见二进制

调试文本没问题，但嵌入式调试大量面对**二进制数据**：串口收到的协议帧、传感器原始报文、Flash 里的内容、DMA 缓冲区。这些字节里大量是不可打印字符（0x00、0xFF、控制符），直接 printf 出来是乱码或屏幕乱跳，人眼无法分析。

hexdump 的思路：**每个字节展开成两位十六进制文本**（0x00~0xFF → "00"~"FF"），任何字节都变成可见字符，一行对齐排列，肉眼就能对照协议文档逐字段核对。

这个"偏移 + hex + ASCII"的格式是**行业标准**：PC 上分析日志、看内核 dump、查固件问题，用的全是同一格式（`hexdump -C`、`xxd`、Linux 内核 `print_hex_dump`）。学一次，PC 端和 MCU 端的日志都能读——对嵌入式开发来说，串口日志和 PC 工具输出经常要并排对照，格式统一才有互认。

## 使用场景（什么时候会用到它）

| 场景 | 例子 | hexdump 帮你看清 |
|---|---|---|
| 串口协议调试 | 雷达/蓝牙/4G 模组返回帧 | 帧头、长度、校验各在哪个字节 |
| DMA/接收缓冲区 | RX buffer 收了什么 | 有没有收到、收到几个字节、内容对不对 |
| Flash/EEPROM 内容 | AT24C02 读回一段 | 写入的数据是否完整、擦除是否为 0xFF |
| 传感器原始数据 | AHT30 六字节报文 | 温湿度位域在报文里的排布 |

一句话：**凡是"这段内存里到底是什么"的疑问，都丢给 hexdump**。

## 效果展示

main.c 里那行调用与串口助手上实际看到：

```c
static uint8_t rxbuf[32] = {0x12,0x34,0x56,0x78, 'A','B','C'};
uart_hexdump(rxbuf, sizeof(rxbuf), "RX BUF");
```

```
RX BUF (len=32):
00000000  12 34 56 78 41 42 43 00 00 00 00 00 00 00 00 00  |.4VxB,BC........|
00000010  00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00  |................|
```

一行三个区域，逐字段解读第一行：

```
00000000   12 34 56 78 41 42 43 00 00 00 00 00 00 00 00 00   |.4VxB,BC........|
└──┬──┘   └──────────────────┬──────────────────────────┘   └────────┬────────┘
 偏移地址                  hex 区（16 字节）                      ASCII 栏
 从 0x10 开始              第 8 字节后多一个空格，                 可打印字符原样显示，
 是第二行的偏移            把 16 字节分成 4+4 / 4+4 两半，         不可打印（<0x20 或 >0x7E）
                          方便肉眼按 4 字节对齐                    显示为 '.'
```

读法示范：`41 42 43` 是 `'A' 'B' 'C'` 的 ASCII，所以右侧 ASCII 栏对应位置显示 `ABC`；开头 `12 34 56 78` 不可打印，显示 4 个 `.`。**hex 区和 ASCII 栏是同一份数据的两种视图**——hex 看精确值，ASCII 碰运气认字符串（看到 "ABC" 就知道是文本内容）。

## 关键概念：偏移是什么、从哪来

**偏移（offset）= 这一行第一个字节距离数据开头的距离**，单位是字节。

数据一长就必须分多行显示。分了行，第二行开头是数据的第 17 个字节（下标 16）、第三行是第 33 个……**人眼往下扫的时候，怎么知道"这行是数据的哪一段"？就靠行首这个偏移数字报位置**：

```
00000000  XX XX XX XX XX XX XX XX XX XX XX XX XX XX XX XX   |第一行：数据的 0~15 字节|
00000010  XX XX XX XX XX XX XX XX XX XX XX XX XX XX XX XX   |第二行：数据的 16~31 字节|
00000020  XX XX XX XX XX XX XX XX XX XX XX XX XX XX XX XX   |第三行：数据的 32~47 字节|
   ↑
0x10 = 16，0x20 = 32 —— 用十六进制报数，正好和 hex 区的进制统一
```

**偏移还有"地址簿"作用**：发现第 200 个字节有问题，先在输出里找 `000000C8`（200 的十六进制）开头的行，再数行内第几列——不用逐行数字节数。协议文档里"帧头在 offset 0、长度在 offset 4"这种描述，直接对得上行首数字。

## 一行 80 列：偏移、hex、ASCII 三段怎么塞进一行的

上面说过这个格式是行业标准，行业标准的来历：CRT 终端时代屏幕一行 80 字符（追到 1928 年 IBM 80 列打孔卡，见文末来源），hexdump 工具为了让一行 dump 在屏幕上**不折行**，把三个区域按固定宽度排进 80 列：

| 区域 | 宽度 | 固定宽度的手段 |
|---|---|---|
| 偏移区 | 8+2 = 10 列 | `%08X` 强制补足 8 位数字 |
| hex 区 | 48 列 | 每字节恒 3 字符（`%02X ` 或 3 空格） |
| 中缝 | 1 列 | 第 8 字节后加 1 空格 |
| ASCII 栏 | 1+16+3 = 20 列 | 竖线包裹，每字节恒 1 字符 |
| **合计** | **79 列 ≤ 80 列** | **任何一行都不折行** |

**"三段能整齐输出"靠的是"每个区域的宽度永远是定值"**：无论数据内容是什么、这行满不满 16 字节，偏移永远占 10 列、hex 区永远占 48 列、ASCII 栏起点永远在同一列。这样屏幕上竖着看，偏移一列、hex 一片、ASCII 一栏，各自成列——人眼沿竖线扫，第 5 列的 hex 永远对应第 5 个字节的 ASCII。这个"宽度恒定"是代码里多处 if/格式符共同保证的，下面逐行看它们各自管哪一段。

这个 79 列的构成同时也是行缓冲 line[80] 大小的依据（第三段详算）。

## 逐行精读：从函数签名开始

原函数整体贴在上面总览里出现过，现在一行一行过。先把完整签名和骨架摆出来，再逐段深挖。

### 第一段：函数签名——三个形参每个都有讲究

```c
void uart_hexdump(const void *data, size_t len, const char *title)
```

**形参 1：`const void *data`——为什么是 void*，为什么要 const**

- `void *` 是"无类型指针"，能接收**任何类型**的地址。hexdump 的用户可能传 `uint8_t rxbuf[]`（字节数组）、`uint32_t adc[8]`（整数数组）、自定义结构体 `&sensor_data`——如果形参写成 `uint8_t *`，传 uint32_t 数组就得在调用点强转；写成 void* 则任何指针都直接兼容（C 里任何对象指针可隐式转为 void*，这是编译器承诺的，不需要写强转）。**"我不关心你传什么类型，我只当它是连续内存"**——这是内存查看类函数的标准签名
- `const` 承诺"本函数不修改 data 指向的内容"。你 dump 一段数据，肯定不想函数偷偷改它。const 是给调用者的合同：传 const 数据进来不用强转掉 const 属性。凡是"只读输入"的指针形参，都该加 const
- 强转 `const uint8_t *p = (const uint8_t*)data;` 在函数第一行（下文详解）——为什么转成 uint8_t*？因为 hexdump 的最小操作单位是**字节**，uint8_t 正是 1 字节无符号整数。对 p[i] 解引用就是第 i 个字节，逐字节遍历天然顺畅

**形参 2：`size_t len`——为什么不用 int**

- `size_t` 是 C 标准为"内存大小/数组下标"专设的无符号类型（32 位机上 4 字节）。sizeof 返回它，malloc 参数是它，"一段内存多长"在 C 里就该用它
- 用 int 的问题：长度永远是正数，int 的负数表达能力纯属浪费；更糟的是调用者传负数（bug）时 int 会照单全收，无符号类型下 -1 变成巨大的 4294967295——虽然也是错，但配合 len 的用法（循环边界）至少不会静默截断。这是习惯问题，标准库全用 size_t，跟着走最稳
- **这不是纸上谈兵，Linux 内核踩过真实的坑**：内核的 `print_hex_dump_bytes()` 曾在内部用**有符号 int** 接收 size_t 的 len，用户 dump 超大缓冲区时 len 被截成负数，`min(len, 上限)` 返回了负数，结果**什么都不 dump，静默失败**。后来把形参改成 unsigned long 才修复（见 [内核源码 lib/hexdump.c](https://elixir.bootlin.com/linux/latest/source/lib/hexdump.c) 的演进）。类型选错，bug 会藏得很深
- 长度和 data 分开传，而不是"约定 data 以某字节结尾"——内存查看函数不知道调用者的数据里哪算"结尾"（0x00 本身就是合法数据），**长度必须由调用方显式给出**。这也呼应 strlen（找 '\0'）和 memcpy（带 len）的分野：文本有终结符，二进制没有

**形参 3：`const char *title`——可选参数的 C 语言写法**

- 标题是可有可无的：有的调用点想标注"这是 RX BUF"，有的只是顺手 dump 不需要名字。C 没有默认参数（C++ 才有），**用 NULL 表示"没提供"**是标准做法
- 所以函数内第一件事就是 `if (title)` 判空——NULL 检查不是可有可无的防御，是这个设计的另一半：调用者可以传 0/NULL，函数必须接得住。漏判的话 `uart_printf("%s...", NULL)` 解引用空指针，硬Fault
- title 同样加 const：函数只读它

**返回值：`void`——为什么不报错**

- dump 是"尽力而为"的调试输出，失败了（缓冲不够、串口忙）调用者也无事可做，返回错误码只会没人检查。调试工具从简

### 第二段：强转 + 标题打印

```c
const uint8_t *p = (const uint8_t*)data;
if (title) uart_printf("%s (len=%u):\n", title, (unsigned)len);
```

**第一行的强转在做什么**：void* → uint8_t*。类型上 void* 转任何对象指针都合法（甚至可以不写强转），**显式写出来的意义是文档**：明示"我把它当字节流处理"。保留 const（`const uint8_t *`）呼应形参的承诺——从 const void* 强转时丢掉 const 是严重错误（后续就能改它了），这里原样带上，类型系统继续替你把关。

注意 p 是"指向 const 的指针"——`*p` 不可改，但 p 本身可以 ++/--。后面只读遍历正合适。

**第二行两个细节**：

- `%u` 而不是 `%d`：len 是 size_t（无符号），格式符对应无符号输出。混用虽然 32 位机常不出错，但 printf 家族的格式符和实参类型不匹配是未定义行为，对齐是好习惯
- `(unsigned)len` 强转：size_t 在某些平台可能比 unsigned 宽（64 位机 8 字节），显式缩窄到格式符真正期望的类型，把隐式转换变成明示的
- `if (title)`：形参设计里说的 NULL 检查，标题为空就跳过整行，dump 照常进行

### 第三段：行缓冲与外层循环——为什么要缓冲、为什么是 16、80 从哪来

```c
char line[80];
for (size_t i = 0; i < len; i += 16) {
```

这一行代码背后有三个问题，一个一个来。

#### 问题 1：为什么需要行缓冲（line[80]）这个中间变量？

先想"不用缓冲"怎么做：每算出一小段文字就立刻发出去——偏移发了、每个字节发了、ASCII 一个一个发。看起来可行，但有两个毛病：

**毛病 1：发送碎片化，串口效率暴跌。** `uart_puts` 底层是 `HAL_UART_Transmit` 阻塞发送，每次调用都有固定开销（函数进入、参数检查、启动发送、等完成）。逐段直发一个 32 字节的数据：偏移 1 次 + hex 最多 32 次 + 中缝 16 次 + ASCII 最多 32 次 + 行尾……**上百次微小发送**，每次 1~3 字节。UART 一字节要约 87µs（115200 波特率，10 位/字节），启动开销摊不薄，总时间远超"拼好 76 字符一次发出"。拼成整行后，32 字节数据只有 2 次发送——**发送次数从百级降到个位**，这是"合并发送粒度"的通用优化思路（网络里攒包、Flash 里攒页同理）。

**毛病 2：发一半发现格式错误，收不回来。** UART 是发出去就收不回的流。逐段直发时，如果拼到后面才发现越界或逻辑错误，屏幕上已经留下了半行残缺输出。先在内存里拼完整行、确认无误再发，输出要么整行正确、要么整行不发——**原子性**。

所以行缓冲的本质：**把"逐字节逐段生成"的计算节奏，和"按行批量发送"的传输节奏解耦**，中间用一小块内存衔接。这块内存只需一行大小（几十字节），代价极小。

#### 问题 2：为什么每行 16 字节、缓冲 80？——格式定下来，缓冲是被格式决定的

每行 16 字节、整行约 80 列，是几十年终端惯例（PC 上 `hexdump -C`/`xxd` 同款，来历见上面"80 列"小节和文末来源）。**对代码来说它们的关系是单向的：先有格式（每行 16 字节 → 三段宽度 → 合计 79 列），再有缓冲（80）**。改格式必须重算缓冲，反过来不用。

#### 问题 3：line[80] 到底够不够？——最坏情况和正常情况都算一遍

**正常情况（整行 16 字节，dump 数据的绝大多数行都是这种）**：

```
偏移区   "%08X  "          → 8 字符数字 + 2 空格        = 10
hex 区   16 × "XX "        → 每字节 2 hex + 1 空格      = 48
中缝     j==7 后 1 空格    →                            = 1
ASCII    " |" + 16 字符 + "|\n"                        = 19
字符串尾 '\0'                                           = 1
─────────────────────────────────────────────────────────
合计                                                  = 79 字节
```

79 ≤ 80，**正常满行就已经贴近上限了**——80 不是留了大余量的随意值，而是恰好够用。

**最坏情况其实和正常情况一样**：仔细回看代码，偏移永远 8+2、hex 区每字节恒 3 字符（`%02X ` 补零 + 空格，不足时补 3 空格占位同样 3 字符）、ASCII 栏最多 16 字符——**任何一行都不可能超过满行的 79 字节**。"最坏情况"就是"满 16 字节的行"，这也是为什么上面算的正常情况就是最坏情况。

**真正会越界的场景是把 16 改大而缓冲不跟着改**：比如把每行 16 字节改成 32 字节，最坏行长变成 8+2 + 96 + 1 + 35 + 1 = 143 字节，line[80] 直接溢出，栈被写穿。**缓冲大小和每行字节数是绑定的**——权威项目的做法是显式算式绑定，[Linux 内核 lib/hexdump.c](https://elixir.bootlin.com/linux/latest/source/lib/hexdump.c) 里 `print_hex_dump` 的行缓冲就是写成一个算式而不是一个裸数字：

```c
unsigned char linebuf[32 * 3 + 2 + 32 + 1];
//                    │     │  │    │  │ └ '\0'
//                    │     │  │    │  └ 32 字节 ASCII 栏
//                    │     │  │    └ 中缝 2 字符（内核中缝比本例宽）
//                    │     │  └ 空格分隔
//                    │     └ 每字节 3 字符（2 hex + 1 空格）
//                    └ 每行最多 32 字节（内核 rowsize 支持 16 或 32）
```

改 rowsize 只动第一个数字，算式自动给出新缓冲大小。**本例的 `line[80]` 是"算好了一次性写死"，内核是"把算式写进代码"**——后者更防手抖，自己写建议学内核。

**兜底问题：万一真拼超了怎么办？** 80 字符格式下不会发生（79<80），但假如格式改错了，防线是 snprintf 本身——它**最多写 size-1 字符 + '\0'，永不越界**，超了会截断而不是写穿栈。所以这套代码的完整性是双保险：设计期算准大小（第一道），运行期 snprintf 硬限制（第二道）。

#### `i += 16` 步进

i 是"本行第一个字节在数据里的下标"。i=0 处理字节 0~15，i=16 处理 16~31……循环次数 = ⌈len/16⌉（向上取整），最后一行通常不满 16 字节——这是下面"补齐"逻辑存在的理由。

### 第四段：偏移区——pos 游标登场

```c
int pos = 0;
pos += snprintf(line + pos, sizeof(line) - pos, "%08X  ", (unsigned)i);
```

**snprintf 链式拼接的完整原理**。先看 snprintf 本身：

```c
int snprintf(char *str, size_t size, const char *fmt, ...);
//            写到哪     最多写多少    格式串
```

- 最多写 size-1 个字符 + 强制 '\0'，**永不越界**——这是它比 sprintf 安全的根本
- 返回值是"本应写入的字符数"（不含 '\0'）。正常时返回实际写入数；被截断时返回"如果 buffer 够大本应写的数"——**无论截不截断，返回值都是"这段输出了多少字符"**，正好用来推进 pos

于是形成固定套路：

```
line + pos       → 从上次写完的位置接着写
sizeof(line)-pos → 剩余容量（保证不越界）
pos += 返回值    → pos 指向下一个可写位置
```

三步一环扣一环：目标位置由 pos 决定，容量限制随 pos 递减，写完 pos 前进。**任何一段都是这个模式，整个函数就是十几段相同模式的串联**——学会一段就会整个函数。

`%08X` 拆开：X = 大写十六进制，08 = 至少 8 位、不足补 0。i=0 打成 `00000000`，i=16 打成 `00000010`——固定 8 位宽让每行的偏移区严格等宽，眼睛扫下来一列对齐。后面的两个空格把偏移区和 hex 区隔开。

### 第五段：hex 区——双循环与补齐

```c
for (size_t j = 0; j < 16; ++j) {
    if (i + j < len) pos += snprintf(line + pos, sizeof(line) - pos, "%02X ", p[i + j]);
    else             pos += snprintf(line + pos, sizeof(line) - pos, "   ");
    if (j == 7) pos += snprintf(line + pos, sizeof(line) - pos, " ");
}
```

**双循环的分工**：外层 i 管"第几行"（每行 16 字节的起点），内层 j 管"行内第几个"（0~15）。`p[i + j]` 就是"本行第 j 个字节"的地址换算——i 定位行、j 定位列，二维平面用一维下标表达，这是数组遍历的基本功。

**`%02X`**：两位十六进制、不足补 0。一个字节 0~255，两位 hex 恰好全覆盖（0xFF），所以每个字节稳定占 3 字符（"XX "+空格）——**等宽输出是行对齐的前提**，如果某字节打成 1 位（"A "），后面全错位。

**`if (i + j < len) ... else 补空格` 的必要性**：最后一行可能不满 16 字节（len=5 时 j=5~15 都越界）。越界读 p[i+j] 是未定义行为（可能硬Fault，至少读到垃圾数据）。两个分支写的都是 3 字符（"XX " 与 "   "），**保证 hex 区占宽恒为 48**——这样最后一行的 ASCII 栏竖着看仍然和上面各行对齐。不补齐会怎样？最后一行 ASCII 栏左移，肉眼对照 hex 和 ASCII 就错位了。**"对齐"的目的正在于此：dump 是给人眼逐列对照用的，横看一行是偏移+hex+ASCII，竖看一列是同一字节的三种视图，任何一列错位整个工具就废了。**

**`if (j == 7)` 的中缝**：第 8 个字节（j=7）后面多打一个空格，把 16 字节劈成两半——实际是 4 字节一组（32 位对齐）更易读。纯为肉眼服务，没有任何数据含义。

### 第六段：ASCII 栏——可打印判断

```c
pos += snprintf(line + pos, sizeof(line) - pos, " |");
for (size_t j = 0; j < 16 && i + j < len; ++j) {
    uint8_t c = p[i + j];
    pos += snprintf(line + pos, sizeof(line) - pos, "%c",
                    (c >= 32 && c <= 126) ? c : '.');
}
pos += snprintf(line + pos, sizeof(line) - pos, "|\n");
```

**循环条件多了 `&& i + j < len`**：对比 hex 区循环只看 j<16。hex 区不满要补空格占位，ASCII 栏却**只打实际字节**——一多一少，正是"hex 区对齐是死的、ASCII 栏跟着数据走"。竖线 `|` 把两个区域视觉隔开。

**`c >= 32 && c <= 126`**：ASCII 可打印区间 [0x20, 0x7E] 的十进制写法。区间外（0x00~0x1F 控制符、0x7F DEL、0x80~0xFF 高位字节）原样打会乱屏（终端把这些当控制指令解释，比如 0x08 回退、0x1B 进入转义序列），统一替换成 `.`。**替换而非过滤**——保持每字节恒占 1 字符，列对齐不破坏。内核同样这么干：`lib/hexdump.c` 里写的是 `(isascii(ch) && isprint(ch)) ? ch : '.'`，判断函数不同、区间语义一致。

**三元 `? c : '.'`**：C 的条件表达式，等价 if/else 但能直接作为 snprintf 的实参——"选一个值输出"的场景比 if/else 紧凑。uint8_t 提升为 int 传入 %c，%c 按"当字符显示"解释，无碍。

### 第七段：收尾与发送

```c
uart_puts(line);
```

拼好的整行交给 [[06_rocketpi_uart_printf]] 里的 `uart_puts`——它内部做 CRLF 规范化（line 尾是 '\n'，自动补 '\r'）再阻塞发出。**拼行和发送分离**：hexdump 只管"拼出正确的一行"，传输细节（CRLF、超时）全权委托，这正是分层。

外层 for 转完所有行，函数结束，无返回值。

## 完整演练：从真实场景到第一行输出

**场景**：调试 I2C 温湿度传感器 AHT30，按手册往 0x38 地址发了测量命令，读回 7 个字节的原始报文，怀疑通信有问题。 Dump 一下看看读到的是什么：

```c
uint8_t aht30_rx[7] = {0x1B, 0x2A, 0x38, 0x66, 0x9C, 0x00, 0x00};
uart_hexdump(aht30_rx, sizeof(aht30_rx), "AHT30 RX");
```

**串口助手上最终打印的结果**（先看结论）：

```
AHT30 RX (len=7):
00000000  1B 2A 38 66 9C 00 00 00 00 00 00 00 00 00 00 00  |.*8f............|
```

对照手册核对：0x1B 0x2A 0x38 是湿度 20 位，0x66 0x9C 是温度 20 位的前 12 位 + 两个状态位……读数在合理范围，通信没毛病。**这就是"代码 → 眼睛能核对的一行文本"的全过程**。注意这里只有 7 字节有效数据，但输出是一整行 16 字节的宽度——正好演示"不满一行"时代码如何处理。下面逐步跟代码走。

### 步骤 1：进入函数，准备字节视图

```c
const uint8_t *p = (const uint8_t*)data;        // p 指向 0x1B
if (title) uart_printf("%s (len=%u):\n", title, (unsigned)len);
```

标题行先打出 `AHT30 RX (len=7):`（7 是 sizeof 数组，不是有效字节数——如果实际只收到 3 字节，调用方该传 3 而不是 sizeof，这点自己用时要注意）。

### 步骤 2：外层循环启动

```c
char line[80];
for (size_t i = 0; i < len; i += 16) {
```

len=7，i 从 0 开始：0 < 7 成立，**进入第一轮（也是唯一一轮——7 字节不满 16，i+=16 后 16<7 不成立，循环结束）**。本例的"最后一行"就是唯一一行。

### 步骤 3：拼偏移区

```c
int pos = 0;
pos += snprintf(line + pos, sizeof(line) - pos, "%08X  ", (unsigned)i);
```

i=0，`%08X` 补零到 8 位 → `00000000`，加两个空格。line 前 10 字符：`00000000  `，pos=10。

### 步骤 4：拼 hex 区——前 7 个真字节 + 9 个补位

```c
for (size_t j = 0; j < 16; ++j) {
    if (i + j < len) pos += snprintf(line + pos, sizeof(line) - pos, "%02X ", p[i + j]);
    else             pos += snprintf(line + pos, sizeof(line) - pos, "   ");
    if (j == 7) pos += snprintf(line + pos, sizeof(line) - pos, " ");
}
```

j 从 0 到 15 逐个过：

| j | i+j<len? | 动作 | line 新增 | pos 变化 |
|---|---|---|---|---|
| 0~6（7 个） | 是（0~6 < 7） | `%02X ` 打真字节 | `1B ` `2A ` `38 ` `66 ` `9C ` `00 ` `00 ` | 10→31 |
| j==7 处 | — | 中缝 | ` ` | 31→32 |
| 7~15（9 个） | **否（7~15 ≥ 7）** | 补 3 空格 | `   ` × 9 | 32→59 |

注意 j=7 这一轮：7<7 不成立，**打的是补位空格**，然后紧接着中缝又加 1 空格——所以第 8 字节位置是个"空格+中缝空格"。此时 line 内容：

```
00000000  1B 2A 38 66 9C 00 00                     
          └── 真 7 字节 ──┘└─ 补位 9 个 3 空格 ─┘
pos = 59（hex 区恒占 48 + 偏移 10 + 中缝 1）
```

**hex 区占宽和满行时一模一样**——不管真数据 7 个还是 16 个，这一段永远是 48+1 列。这就是上面说的"宽度恒定"，靠 `if/else` 两分支等宽实现。

### 步骤 5：拼 ASCII 栏

```c
pos += snprintf(line + pos, sizeof(line) - pos, " |");
for (size_t j = 0; j < 16 && i + j < len; ++j) {
    uint8_t c = p[i + j];
    pos += snprintf(line + pos, sizeof(line) - pos, "%c",
                    (c >= 32 && c <= 126) ? c : '.');
}
pos += snprintf(line + pos, sizeof(line) - pos, "|\n");
```

- 先打 ` |`（pos 59→61）
- 内层循环**多了一条 `i + j < len`**：j=0~6 就停（7≥7 时退出），**只打真数据**，没有补位
  - 0x1B（27，<32 控制符 ESC）→ `.`
  - 0x2A（42，`*`）→ `*`
  - 0x38（56，`8`）→ `8`
  - 0x66（102，`f`）→ `f`
  - 0x9C（156，>126）→ `.`
  - 0x00 ×2（<32）→ `.` `.`
  - ASCII 栏得 `.*8f...`，7 字符
- 行尾 `|\n`（pos 61→69）

### 步骤 6：发送

```c
uart_puts(line);
```

整行 68 字符（+'\0' 共 69）一次性发出，uart_puts 把结尾 `\n` 补成 `\r\n`。串口助手显示：

```
00000000  1B 2A 38 66 9C 00 00 00 00 00 00 00 00 00 00 00  |.*8f............|
```

等一下——**屏幕上 ASCII 栏前面那片空白哪来的？** 就是步骤 4 补的 9 组 3 空格 + 中缝：真数据只到第 7 列，hex 区却按 16 字节的宽度占满，ASCII 栏从第 61 列开始——**同一列**。这行不满 16 字节，但三个区域的起点、终点和满行完全一致，竖着看和其他行永远齐。

i+=16 后 16 < 7 不成立，外层循环结束，函数返回。

### 演练复盘

这一行输出的本质是代码里三种"宽度守护"的合力：`%08X`（偏移恒 8 位）、`%02X ` vs `   `（hex 每字节恒 3 列）、ASCII 只打真字节（数据如实）——**格式骨架刚性、数据内容如实**。所以无论 dump 3 字节还是 4096 字节，每一行都长一个模子，人眼只需要学会读一次。

## 设计复盘：如果让你自己写

把上面的逐行结论收敛成一份"设计清单"——照着它就能从零写出同类函数：

1. **定输出格式**（三段式、每行 16 字节、补齐规则）——格式先于代码；每行 16 字节与 ~80 列是几十年终端惯例，跟着惯例走可与 PC 工具输出互认
2. **签名设计**：数据用 `const void*`（通用）、长度 `size_t`（显式传，别用 int——内核踩过 int 截断 len 的坑）、可选信息用 `const char*` + NULL 约定
3. **算行缓冲大小**：按格式逐段累加最坏长度（本例=满行 79），写缓冲时把算式写进代码（学内核 `32*3+2+32+1`），别写裸数字
4. **核心循环**：外层行、内层列，`i+j<len` 判越界，hex 区不满补齐、ASCII 栏只打实际字节
5. **拼接统一用 snprintf 游标模式**：`line+pos`、`sizeof(line)-pos`、`pos +=` 三件套，永不越界（运行期兜底）
6. **可打印字符判断** [0x20,0x7E]，区间外替换 '.'（内核同款逻辑）
7. **发送与拼行分离**，整行合并发送减少阻塞次数（发送次数从百级降到个位）

这七步不止适用于 hexdump——任何"把二进制/结构化数据变成人可读文本"的函数（日志格式化、协议打印、CSV 生成）都是同一套骨架。

## 快速上手：把 hexdump 当调试按钮

往任何可疑位置插一行：

```c
uart_hexdump(&something, sizeof(something), "checkpoint");
```

看输出、对照数据手册、定位问题，再删掉。它和断点调试互补：断点看"那一刻的状态"，hexdump 看"一段时间内数据怎么变"（连打多次就能看到变化过程）。
