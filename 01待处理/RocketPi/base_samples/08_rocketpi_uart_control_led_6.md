# 同类需求识别与设计迁移：这个骨架还能用在哪

> 学完 08 + [[08_rocketpi_uart_control_led_5|函数协作全景]]，掌握的不该是"一套控制 LED 的代码"，而是**一套可迁移的设计模式**。这篇回答两个问题：遇到新需求时，怎么识别"这是同类问题"？确认同类后，怎么把 08 的设计复制过去、哪里要改？

## 一眼识别同类需求的四个信号

当一个需求摆到面前，出现以下任一信号，08 的骨架就适用：

1. **设备只靠一根串口线与人（或另一个 MCU）对话**——没有屏幕、没有键盘，唯一的交互通道是 UART
2. **对端发文本，设备要"听懂"并做事**——无论是人敲的命令、上位机发的配置，还是模组发的事件通知
3. **一条消息能映射成有限的动作集合**——能列得出"收到什么 → 该做什么"的对应关系
4. **消息有明确的边界**——换行、分号、帧尾符、空闲时间，总之能分清"这条到哪结束、下条从哪开始"

反之，如果要求的是高带宽流式传输（音频/图像）、或字节序敏感的二进制结构，文本骨架就不合适（选二进制状态机路线，见 [[08_rocketpi_uart_control_led_4|协议谱系]]）。

## 迁移方法论：三张表填完，设计就完成了

把 08 的设计过程压缩成三张待填的表。任何同类需求，填完这三张表，代码结构自动成形。

### 表一：命令表（对应 g_led_config + token 解析）

回答"有哪些词汇、映射到什么资源"：

| 列 | 08 的填法 | 举例：电机控制需求 |
|---|---|---|
| 资源下标 | led_index 0..2 | motor_index 0..1 |
| 硬件引用 | GPIO_Port/Pin | TIM 句柄 + 通道号 |
| 别名 | B/BLUE/LED_B | M1/MOTOR1/LEFT |
| 值域 | bool 开关 | int32_t 转速 RPM |
| 特殊关键字 | ALL | ALL / STOP（急停） |

这张表决定了配置结构体的字段和查表函数的形态。**规律：资源有限且可枚举 → 表驱动；资源动态 → 表换成链表/动态注册**（参考 [[08_rocketpi_uart_control_led_1|交互终端笔记]] 的两种注册流派）。

### 表二：中间表示（对应 LedCommand_t）

回答"解析完成后，执行前，信息以什么形态存在"：

```c
typedef struct {
  uint8_t  motor_index[MOTOR_TOTAL];  // 表一的资源下标
  int32_t  speeds[MOTOR_TOTAL];       // 表一的值域
  size_t   motor_count;
  size_t   speed_count;
} MotorCommand_t;
// 校验规则：speed_count==1（广播）或 == motor_count（一一对应）
```

**规律：字段全部来自表一，再加 count 字段和一条语义校验规则**。值的类型由表一的"值域"列决定——bool 就用 bool，范围值就用带符号整型，别用字符串存中间状态。

### 表三：应答格式（对应 report_result/report_error）

回答"怎么把结果翻译回给对端"：

| 项 | 08 的填法 | 设计规则 |
|---|---|---|
| 成功应答 | {"status":"ok","led":[...],"state":[...]} | 回显解释后的结果，不是回显原文 |
| 失败应答 | {"status":"error","msg":"..."} | 机器可读，msg 用固定短语 |
| 自描述 | 上电发 gpio_map | 资源可枚举时必做，上位机免查文档 |
| 应答缓冲 | 192 字节按最坏情况推算 | 最坏情况 = 全部资源 + 最长名 + 模板开销 |

三张表填完，函数清单自动出来：**表一→find/查表函数；表二→parse 系列 + apply；表三→report 系列**。加上固定不变的行组装（handle_input_byte 几乎可以原样复制）和 I/O 网关（send_string），整套方案的函数骨架就齐了。

## 场景演练一：传感器实时查询命令（最贴近 08 的直接迁移）

需求：板上接了 AHT30 温湿度传感器（14 例的预告），希望在命令终端敲 `temp` 就回当前温度。

**识别**：一根串口线 ✓、文本命令 ✓、动作有限（查询/设置阈值）✓、换行分帧 ✓——同类。

**三张表**：命令表（temp/hum/all 三个命令，无资源下标，值域 float）→ 中间表示（其实只需要一个枚举：查哪个传感器）→ 应答（{"temp":25.3,"hum":60.1}）。

**结构变化点**：这个例子比 08 还简单——没有资源下标数组，中间表示退化成一个 enum。但骨架原封不动：行组装复用、解析用 find_json_value 或直接 strcmp、执行层调 HAL_I2C 读传感器、汇报 snprintf。**从最简单的查询命令到 08 的批量控制，是同一骨架的伸缩，不是两种设计**。

这里埋一个重要预告：查询命令的执行层要碰 I2C 总线（阻塞几毫秒），而 08 的执行层只碰 GPIO（微秒级）。**执行层越慢，"阻塞式主循环"的代价越明显**——这是后面把接收层改造成中断/DMA 驱动的真正动机，也是 07 与 08 关系的深层原因。

## 场景演练二：配置存取命令（引入持久化的变体）

需求：参数（如 LED 默认状态、设备编号）要能通过命令修改，断电不丢——即 `set id 42` 写入 Flash，上电读回。

**骨架复用**：命令表/解析/应答完全不变。变化只发生在执行层：

```
set_led_state（写 GPIO，微秒级）  →  flash_write（擦写一页，几十毫秒！）
```

**新问题与解法**：几十毫秒的阻塞写会让主循环失去响应——但响应对象是谁？本方案主循环本来就在死等串口，所以短暂阻塞无碍。真正的风险是：**写入期间串口还在收字节吗？**（HAL_UART_Receive 阻塞模式下，字节在接收移位寄存器只能暂存一两个，会丢）。

设计上的应对：要么写入前发一句 `{"status":"busy"}` 告知对端稍候；要么把接收层换成中断驱动（字节进环形缓冲），执行层慢慢写。**这就是"执行层耗时决定接收层架构"的判断链条**：先测最坏执行耗时，再看对端是否会在这个窗口发数据，两者共同决定要不要升级接收层。

## 场景演练三：MCU 对模组发命令（AT 框架，立场反转）

需求：主控通过串口指挥 ESP8266 连 WiFi（37/38 例的预告）。这次**设备不是服务器而是客户端**：MCU 发 `AT+CWJAP="ssid","pwd"`，模组回 `OK` 或 `ERROR`。

三张表填法反转：

- **命令表**：命令在模组侧定义（查模组手册），MCU 侧只需存"命令模板+期望应答"：`{"AT+CWJAP=\"%s\",\"%s\"", "OK", 15000ms 超时}`
- **中间表示**：{命令 ID、参数缓冲、期望应答、超时时刻}——多了**时间维度**
- **应答**：不是自己生成而是等待、匹配、判断成败

**新引入的部件是超时机制**：发完命令启动 HAL_GetTick 计时，行结算收到 "OK" → 成功；收到 "ERROR" → 失败重试；计时到 → 超时失败。骨架的"收→解→行"三幕不变，只是第四幕的"执行"变成了"等待"，中间表示多了 deadline 字段。**同步等待会卡主循环，工程化的 AT 框架会把等待改成状态机**（发完就返回，应答到达时再推进）——这是 11 之后值得回头看的设计升级。

## 场景演练四：多设备共享一条串口（识别"不同类"的反例）

需求：RS485 总线上挂 8 个从机，主机广播命令、指定地址的从机应答。

表面看完全同类（串口、文本命令、有限动作），但有一个本质差异：**一条线上有多个对端，消息必须先分清"发给谁"**。08 的骨架里没有"地址"这个概念，硬套会翻车。

正确的迁移姿势：在**行组装与解析之间插入一层**——地址过滤。收到的行先看首字段 `#3,temp`：地址非本机则整行丢弃（解析层根本不启动），本机才往下走。**骨架的层是可插拔的**：本例插入地址层，13 的雷达帧会插入校验层（异或/CRC 核对不过整帧丢弃），AT 框架会插入 URC 分流层（模组主动上报 vs 应答响应走不同分支）。识别出需求后，**先画 08 的六角色流水线，再问"我的需求需要插入哪一层"**，而不是从零开始想。

## 通用设计流程总结（六步）

1. **识别信号**：一根串口线 + 文本消息 + 有限动作 + 可辨边界 → 用本骨架；否则换路线（流式→DMA 环形缓冲，二进制→状态机+帧校验）
2. **填三张表**：命令表（词汇→资源）、中间表示（字段+校验规则）、应答格式（成功/失败/自描述）
3. **画六角色流水线**：传输→行组装→解析→校验→执行→汇报，检查有没有需求要插入的额外层（地址/校验/分流）
4. **评估两个耗时**：执行层最坏耗时（决定要不要升级接收层）、应答缓冲最坏长度（决定容量）
5. **定防御策略**：超长清零重来、空行静默、重复去重、错误结构化——这四条 08 的答案几乎总能照搬
6. **回填自检十问**（[[08_rocketpi_uart_control_led_2|数据结构与 API 设计]] 末尾）验证设计闭合

这六步走完，代码只是把表格翻译成 C 而已。08 用三颗灯演示了这个流程的全部决策点——**它不是"一个例程"，是一张可复用的设计图纸**。
